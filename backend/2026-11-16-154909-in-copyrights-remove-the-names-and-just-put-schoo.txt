  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ PDF uploads and serving         │ Storage buckets, with public read and │

  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Public registration (POST       │ RLS insert-only for anonymous users   │
  │ /api/registrations)             │                                       │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Approve/reject with audit trail │ Admin update, plus a Postgres trigger │
  │                                 │  that writes the audit row            │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Excel export (export.xlsx)      │ Client-side export with SheetJS, or   │
  │                                 │ CSV                                   │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ SMTP emails                     │ An Edge Function (see below)          │
  └─────────────────────────────────┴───────────────────────────────────────┘

  What to watch for
  - Email is the one piece that still needs server-side code. A small Supabase
    Edge Function can send it through Resend or Gmail SMTP. Firebase Cloud
    Functions needs the paid Blaze plan for outbound calls, so that's another
    point for Supabase.
  - Validation now has to live in the database. That covers team size limits,
    duplicate checks, registration dates and the PDF size and type limits. Use
    CHECK constraints, triggers or RLS policies, because anyone can call the API
    directly and skip your frontend checks.
  - RLS is the security boundary. Registrations contain personal data, so they
    must not be publicly readable. This is the part to get right.
  - Hosting gets simpler. Your current JSON and PDF files need a persistent
    disk. With Supabase you only host the static frontend, for example on Vercel
    or Netlify, and the free tier should cover the traffic for one competition.

  It's a rewrite of the data layer and about 10 API calls in main.jsx, not a big
  job. I can do the migration if you want. Say so and I'll start with the
  schema and RLS policies.

❯ how now mails work when deployed in vercel                                    

● Your current email code won't work as it is on Vercel. Here's why and what to
  do.

  Why it breaks
  - Emails currently go out from the FastAPI backend through Gmail SMTP, using
    SMTP_USER and SMTP_APP_PASSWORD. The send runs in a background
    threading.Thread.
  - Vercel runs serverless functions. They freeze as soon as the response is
    returned, so a background thread can be killed before the email goes out.
    You have to await the send before responding.
  - Vercel also has no persistent disk, so the JSON and xlsx storage fails too.
    That's why moving to Supabase makes sense.

  Options for email on Vercel
  1. Vercel Serverless Function (/api/send-email.js) using Resend, or nodemailer
     with Gmail SMTP. Keep the secrets in Vercel environment variables and
     await the send.
  2. Supabase Edge Function, if you move to Supabase. A database trigger or the
     admin's approve/reject action calls it. This keeps all backend logic in one
     place.

  Which email provider
  - Gmail SMTP with an app password works from serverless. It's limited to about
    500 emails a day, and the mail sometimes lands in spam. It's fine for a
    small competition.
  - Resend (free tier, 100 emails a day, 3,000 a month) is more reliable. For
    the "From" address to be @sastra.edu you'd need DNS access to verify the
    domain. Without that, it sends from Resend's test domain and can only
    deliver to your own address.

  My suggestion: use a Vercel function or Supabase Edge Function with Gmail SMTP
  first, since you already have the credentials. Switch to Resend if you need
  better deliverability or higher volume. The email_test_mode flag you have
  uncommitted can stay, so you can test without mailing real coaches.

❯ if i migrate to supabase, frontend will still be in vercel right              

● Yes. The frontend stays on Vercel as a static site, and Supabase only replaces
  the backend.

  - Vercel serves the built React app (frontend/). It calls Supabase directly
    with the @supabase/supabase-js client.
  - Supabase holds the database, auth, PDF storage and the email Edge Function.
  - Environment variables: set VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY in
    Vercel. The anon key is meant to be public, because RLS protects the data.
    Never put the service_role key in the frontend. Keep the email SMTP secrets
    in Supabase's function secrets, not in Vercel.
  - Routing: if you use hash links like #competition, you don't need any rewrite
    config. Otherwise, add a rewrite to index.html.

  The backend/ folder would no longer be deployed anywhere, and you could delete
  it once the migration works.
